# Public strategy cues and background decisions

The pinned selector shows one AI faction's committed public plan. A dashed corridor and a faction-letter diamond mark its current public route and strategic waypoint. The target is not a promise about the next action. The view reports realized progress, stalled own decisions, completion, and reassessment from the engine's post-action observation. Human mode excludes the human faction from the AI selector; turning the route off does not change play.

The presentation explicitly copies the public intent fields and never reads `plannerMemory`. No hand, draw order, predicted card action, or search diagnostics are rendered. Existing supply, turret, airport, and neutral-warning overlays remain available. The new route is static, including with reduced motion enabled.

Continuous decisions run in `autohex-ai-worker.js`. Each request contains only the acting faction's observation (public board plus that faction's hand and private planner memory). The returned action remains unchanged for the engine to validate and commit. The main thread checks request ID, scheduling generation, ply, actor, running state, and foreground visibility. Pause, speed changes, replay, restart, visibility loss, and campaign expiry cancel pending work; idle workers are reused. Manual paused single-step and browsers without Worker support use the same bounded synchronous policy.

The campaign retains its foreground monotonic clock and default 0.30-second inter-action delay. Background computation time counts as active campaign time. Computation does not stop board navigation or the campaign clock. `autoHexPlanningDebug()` separates worker computation time from request-to-delivery latency, with a bounded 256-sample history and counts for worker/synchronous decisions. It does not expose planner contents.

Stable controls and inspection APIs:

- `#plan-faction`, `#plan-focus`, `#plan-title`, `#plan-stage`, `#plan-reason`, and the accessible `#plan-progress` progress bar.
- `autoHexPlannerDebug()` returns the selected public intent and bounded route.
- `autoHexPlanningDebug()` returns computation/latency samples and execution modes.
- `autoHexUI()` includes pending worker identity, ready/fallback state, and existing timer/camera information.

`browser.json` and `worker-browser.json` record a runnable checkpoint, including all seven runtime source hashes. The functional suite uses actual DOM/canvas controls and virtual main-page time; opening screenshots are staged by 120 legal AI actions and disclosed model time. The Worker suite holds actual calculated responses to inject stale, mismatched, and duplicate deliveries. These are not ten-minute elapsed-time evidence. Both suites must be rerun against the final engine/planner bytes if those change.

The old virtual-clock browser suites now wait for real Worker completion before asserting an AI move. Their reports are directed into this folder rather than replacing published evidence. `autohex_clock_browser.py` separately checks stale RAF timestamps with normal Worker execution and a deliberately slow synchronous fallback.

`autohex_planner_performance.py` measures two real 30-second foreground intervals after a staged 180-action position. It records worker computation, main-thread waiting, action application, frame gaps, long tasks, and actual selector/target input latency. A mobile viewport is browser emulation on this host, not a physical-device performance claim. `autohex_live_browser.py` additionally hashes the planner and worker and records public plan transitions/progress and final-minute board activity through a real 600-second campaign. The rejected v1 source hashes are engine `0c5b3137…`, planner `2e222d25…`, UI `fb886197…`, and worker `0c7ba91f…` (full hashes are in each JSON report). The two 30-second performance samples already match this v1 runtime. Desktop/mobile worker computation p95 was 120.6/140.0 ms, delivery latency p95 134.3/174.7 ms, and frame interval p95 33.4/33.4 ms. Main-thread long tasks and occasional larger frame gaps remain visible in the report; this is not a claim of stutter-free physical-phone performance. The v1 600-second campaign completed alongside the disclosed model-study/full-suite workload; its results are preserved in `live-v1/`. This candidate was rejected for objective-quality regression and is not the shipping build. The real campaign had zero goal arrivals; sustained combat and passing lifecycle tests do not establish useful strategic play. A corrected engine needs new source-matched campaign and quality evidence.

The rendering correction uses two reused canvas layers around the animated effects. Normal view/camera/selection/plan/inspection/supply/reduced-motion changes repaint the layers; effect ticks reuse them. `autoHexRenderDebug()` reports bounded canvas memory, static rebuilds, composites, and minimap paint counts. The same-position pixel tests include frozen effects and actual mobile pinch/zoom. Full timing comparisons and remaining tails are documented in [browser-validation.md](browser-validation.md).
